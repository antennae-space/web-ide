# AI plugin

The Assistant, the Agents tool, doodles and the board of a conversation. It provides the `assistant` and `agents` capabilities. A built-in plugin: [plugins.md](../../docs/design/plugins.md); `plugin.json` is its manifest.

- **Pod** (`*.go`, package `ai`): The `assistant.*`, `llm.*`, `agents.*` and `models.*` methods: the turn loop and its tools, sub-agents, the Orchestrator, compaction, the board, the Agents tool. The shared parts are lent by the pod: the interface calls of a window `Pod.UICall`, the saved commands, the previews, the tools of the other plugins, the push notifications. The plugin owns the model servers, their keys and the conversations (`LLM`, made in `Register`, closed in `OnStop`; its keys are the `llm` map of the synced vault, `Host.Vault`) and the sessions of the agents, a part of the runtime of a local project (`agents.go`); the Questions tool reads both through `Host.Questions` (`chats.go`: `ChatLoc`, the questions of the conversations), the Kanban through the `agents` capability (`caps.Agents`). `mcp.go` the MCP tools on the conversations linked to a ticket (`kanban_conversation`, `kanban_reply`, `kanban_answer`, through `Host.MCPTool`; Claude Code's replies); `notify.go` the push notifications of a conversation; `exports.go` what the tests of `pod/server` read (`LLM`, `ChatLoc`, `AgentsOf`, `NoteAsks`); the conversations that ran are taken back on `OnStart`, saved on `OnStop`. The tool kit shared with the MCP is the core's `pod/assistant`.
- **Packages** of the plugin (#138), not `internal/` but `stats`, since the tests through the RPC of a whole pod (`pod/server`) set fake model servers and read the conversations:
  - `llm/`: Model servers, chat completions as jobs that survive the page, the images of `generate_image` (`images.go`: the OpenAI images API, the image server and model of `llm.image`), conversations (SQLite), instructions and skills
  - `engine/`: The engine of the assistant apart from the loop: the conversation as stored (`types.go`: `Chat`, `Message`, the modes), its load (`chat.go`), the system prompt and its templates (`prompt.go`, `texts.go`, the instructions of the roles of a ticket, on the lines and the agent rules of `pod/assistant/rules.go`; the prompt stays the same during a conversation, for the prompt cache of the servers: the ticket is read with `kanban_get`, the date and the active file are noted on the messages of the user by `Stamp` when they change and sent at the end of their content, `withContext` in `assistant_loop.go`), the tools offered in each mode (`defs.go`: `ToolsFor`), the Orchestrator, the sub-agents (`subagents.go`), the pages of the board (`pages.go`)
  - `acp/`: Agents tool: ACP client of the CLI agents (Claude Code, opencode, pi), one process per session in the keeper (piped, `sh -c 'exec "$@" 2>>log'` so that stderr stays apart) or in the pod without keeper; the JSON-RPC lines go through a queue per session (the reader of the keeper never waits); the thread built from `session/update` (`transcript.go`, the relative paths of tool calls made absolute from the cwd), saved with the output offset and the awaited prompt id so that the next pod follows the process again; a process that ends is restarted and `session/load`ed (3 ends in a minute stop it); the catalog finds the adapters in the `PATH` or `<data>/acp` and installs them with npm; each turn is timed (the open permissions apart) and recorded with its tokens per model in `turns.jsonl` (`stats.go`: Claude's `_meta.quota.model_usage`, opencode's `usage` and running cost, pi's session file through `~/.pi/pi-acp/session-map.json`), priced by `prices.go` (embedded table + `<data>/prices.json`) when summed; the context ring takes `usage_update`, and during a turn of pi or opencode (which tell it only at its end) `live.go` reads the tokens of the last step (pi's session file, opencode's `opencode.db` read only); `Agent.Hidden` adds the commands an agent runs without listing them (opencode's `/compact`); `Deps.MCP` is the MCP server of the IDE given to the agents that speak MCP over HTTP (`agentsMCP` of the plugin: the listen address, or `MCPBase` in tests); `prompt.go`: the content blocks of a prompt (text, `resource_link` per existing `@path`, images when `promptCapabilities.image`, texts), its images kept as files next to the session (`<id>/img-N`, served by `agents.image`) so the session file stays small, and the queue of the prompts sent during a turn (saved, sent by `endTurn` and after a start); the questions of the agent (`ask.go`): permissions and the forms of `elicitation/create` (declared in `clientCapabilities`: Claude's AskUserQuestion) are entries open until answered, withdrawn by `$/cancel_request`, cancelled by Stop, listed by `Manager.Questions` with the last agent message
  - `internal/stats/`: Measures how the assistant worked in a conversation: speeds, time generating, thinking and in each tool, failures of tools, context and compactions (token counts by part are estimates)
  - `internal/prices/`: The API prices of the models (and `<data>/prices.json` of the user): the cost of the turns of the agents (`acp/`) and of the answers of the assistant
  - `internal/quota/`: The daily quota: the windows of the Claude subscription read from its OAuth usage endpoint (not documented: any error or unexpected shape gives no quota, logged once) with the token of Claude Code (`~/.claude/.credentials.json`, read only, sent to that endpoint only; `WEBIDE_QUOTA_URL` replaces it in the tests), one read shared by every window for 2 minutes and read again after a turn (30 s apart at most); the rest of the day is today's share of the 7-day window (a seventh, the window starting 7 days before its reset) minus what is used, in percent of one share. And the budget of the plugin's setting `daily_budget` (dollars a day) minus the cost since local midnight of the turns of the agents and of the answers of the conversations (`quota.go`: `llm.quota` gives both, the `llm.quota` event at the end of a turn); the bar of a session takes the plan's when Claude Code runs on it (`Info.Subscription`), else the budget; the Assistant's the budget, on a model with a price only
- **History sent to the model** (`apiMessages`, `assistant_loop.go`): it only grows, so that a server keeping a prompt cache (llama.cpp, Strata, the paid APIs) reads only the new messages: the request of a step starts with exactly the messages of the request before it. The reasoning of every answer goes back as it was received (a chat template that does not want the older ones drops them on the server; `estimateTokens` counts it); the image of a board page drawn goes in a user message right after the tool results of its step; a failed answer is set aside (`unsent`) only while it is the last message; the nudge after a stuck answer takes its place and stays there; a pending tool result (questions, a capture, a parent's answer) is filled before the next request. Only a compaction rewrites it (`Compacted`, the summary). A local model (`Caps.Local`: a llama.cpp server or llama-swap, whose chat template puts `reasoning_effort` at the top of the prompt) keeps one effort per conversation, its first (`Chat.Effort`); each later change of the dynamic effort is an effort note (`Message.EffortNote`, `assistant_effort.go`) on the last message sent: a system turn after it when the template takes one in the middle (`Caps.SystemTurns`: DeepSeek, by the model id), else its text appended to it (Qwen's templates refuse a late system message, and drop the reasoning before the last user message: never a new one). DeepSeek reads its trained line (`Reasoning Effort: N (range 1-100, ...)`: low 50, medium 62, xhigh 100, the IDE's Max), the others the sentences of Qwen's template. Cloud providers and Ollama get no effort parameter, as before; an answer still records the effort it was asked with. The system prompt stays the same too (the date and the active file go on the user messages, `withContext`, the effort note after them); only the tools offered follow the mode.
- **Files of a conversation** (`assistant_files.go`, #242): a successful `edit_file` or `write_file` notes its absolute path on the conversation (`Chat.Files`, listed by `llm.chats.list`); the files a command changes are not known. A session of the Agents tool keeps those of its completed `edit`, `delete` and `move` tool calls (`Info.Files`, `acp/transcript.go`: `changedFiles`; a session saved before gets them from its thread on load). The Explorer shows them under the conversation ([explorer.md](../../docs/design/explorer.md)).
- **Root of the Explorer** (`web/explorer.ts`, #243): *Conversations & Agents*, the active conversations and the sessions of the agents with their sub-agents and their files ([explorer.md](../../docs/design/explorer.md)); the list of the conversations is loaded at the opening (`opened`) for it.
- **Consoles of a conversation** (`assistant_shells.go`): `run_command` and `run_saved_command` record the console they started on the conversation (`Chat.Consoles`); `assistant.shells` lists the ones still running (and drops the ended ones from the conversation), `assistant.shells` events tell the windows when one starts or ends (a watcher looks at the console once a second). The bar shows the count.
- **Page** (`web/`, the chunk `plugin-ai`): `llm/` the Assistant tool: state (the conversation shown is the desk's, `deskChat`; a detached window only starts on it), turn loop, tools, prompt, its bar `TopBar.tsx`, on top of the message box (time and cost, shells, parent, children, the daily quota `QuotaPart.tsx` shared with the Agents tool, then the ticket and the role on the right — `Chat.GenMs` and `Chat.Cost` (`assistant_cost.go`: the cost the provider tells, else the tokens at the price of `internal/prices`, shared with `acp/`), summed by the pod at each save, plus the `genMs` of its children in the list of the conversations), the message box shared with the Agents tool: its frame `ComposerShell.tsx` (queue, attachments, dictation line, full screen, mic and paperclip, send / stop, the keys and ↑ / ↓; `focusComposer` and `suggest` by draft key), the drafts by key `drafts.ts` (text in the session of the tab, attachments, doodles), its editor `MessageBox.tsx`, each backend an adapter with the pills of its bar (`Composer.tsx`, `agents/Composer.tsx`), the aliases of its `/` list `aliases.ts` (the presets, the list of the synced settings, `aliasItems`: a command keeps its name), attachments, speech recognition (`transcribe.ts`: Whisper in a worker; live dictation from `pcm-worklet.js`, a file of its own since the relay's CSP refuses a `data:` module, through an energy VAD into segments transcribed again until a pause commits them, written in the box by `liveDictation` of `MessageBox.tsx`), sub-agents `SubAgents.tsx`, doodles `llm/doodle/`, the board of a conversation `llm/board/` (its pages from the doodles and images sent, `board_draw_*` and `generate_image`, `assistant_image.go`), the switch of its views `ViewSwitch.tsx` (Chat, Board, Stats; state in `board/pages.ts`), the follow of the end of a thread `llm/stick.ts` (shared with the Agents tool: any growth follows, a move up stops it, a message sent resumes it), app previews `PreviewCard.tsx`, its interface tools `uiTools.ts`; `agents/` the Agents tool: the switch of `llm/ViewSwitch.tsx` on each session, its board `pages.ts` (the images sent, given to `llm/board/Board.tsx` as a `BoardSource`) and its statistics `AgentStats.tsx`, its bar `StatusBar.tsx` (work time · cost of the session, the daily quota, the ticket of its worktree and the role, sharing the ticket parts of `TopBar.tsx`), sessions of the worktrees of the window and their threads, tabs (those open on the desk, `api.desk`: ✕ hides a session, *Stop the session* ends it, the + opens the others), launcher, permission cards, the follow mode; `plugin.ts` the gateway, whose `on` keeps the events subscribed before the activation.
- **E2e** (`e2e/`, run by `e2e/run.sh`): agent, agents, chat, doodle, llm, orchestrator, plan, subagents, speech.

Its unit tests run on a fake pod (`harness_test.go`), with `go test ./plugins/ai/...`; those through the RPC of a whole pod are in `pod/server`.

The page module imports the plugin API only (`@ide/api`, `@ide/types`, `@ide/capabilities`); the Go package imports the core of `pod/`.

AI imports no code of the Kanban (#158): it reaches it through its methods (`Pod.CallPlugin`, `kanban_client.go`): its kanban tools run in the Kanban (`kanban.assistantTool`, with the conversation), it reads a ticket (`kanban.get`), its Markdown (`kanban.markdown`), the ticket of a worktree (`kanban.worktreeTicket`), links and renames its conversations (`kanban.chat.link`, `kanban.renameChat`); built-in or external, the Kanban answers the same. No package of `pod/` imports the AI's packages (`pod/plugins/builtin` registers the plugin), and the Kanban reaches the AI through `caps.Agents` only.
